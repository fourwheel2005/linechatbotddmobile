# ผลตรวจสอบและแนวทางปรับ Flex Card

ตรวจวันที่ 19 กันยายน 2026 จาก source code ใน workspace นี้ รายงานส่วนด้านล่างเป็นข้อเสนอจากการตรวจครั้งแรก ส่วนสถานะการแก้จริงล่าสุดระบุในหัวข้อถัดไป ยังไม่ได้ส่งข้อความจริงผ่าน LINE

## สถานะล่าสุด: แก้เฉพาะดีไซน์ตามคำขอเพิ่มเติม

- แก้เฉพาะ JSON 4 ใบใน src/main/resources/flex ไม่แก้ Java, Business Logic, state, ราคา หรือระบบส่งข้อความ
- เอาแถวรหัสลูกค้าที่แสดงออกจาก approval card ตามภาพอ้างอิง แต่คง userId ใน postback data ทุกปุ่ม
- ลดหัวข้อบริการ xl เป็น md เพิ่ม wrap ปรับ padding 16px และใช้พื้น header สีอ่อนกับข้อความเข้ม
- แสดงรายละเอียดรุ่นเต็มแถวในกล่องสีอ่อน เอา label “รุ่น” ที่ซ้ำกับค่าจาก flow ออก
- ปุ่มใช้ความสูง md สีหลักเขียวเข้ม #047857 และปุ่มรองเทาอ่อน; approval ยังเป็นปุ่มคู่เพื่อรักษาความกระชับ
- Welcome และ emergency จัดปุ่มเป็นแนวตั้งเต็มความกว้าง ส่วน success คงปุ่มเดียวเต็มแถว
- Welcome ลด hero จาก 20:13 เป็น 3:1 และใช้ fit ให้ภาพอยู่ครบในพื้นที่; คง URL และข้อความต้อนรับเดิม
- เหตุผล/รายละเอียดในการ์ด emergency และ success วางใต้ label เต็มความกว้าง
- คง action ทั้งก้อนเหมือนต้นฉบับ รวม type, label, text, data และ displayText จึงยังไม่เปลี่ยนถ้อยคำสถานะหรือแยก approval สองบริบทตามข้อเสนอเดิม
- Recheck: action ทุกปุ่มเท่าเดิม, placeholder ครบ, ไม่มี userId ในข้อความที่แสดง, text ทุก component เปิด wrap, JSON ทุกไฟล์ parse ได้ และ git diff --check ผ่าน
- LINE SDK 8.4.0 + ObjectMapper จาก LineConfig จริง: deserialize/serialize ทั้ง 4 templates ผ่านและคงทุก property ที่กำหนดไว้
- รัน ./gradlew test --offline หลังแก้: ผ่าน 68 tests, 0 failures/errors/skipped
- ยังไม่ได้ validate ผ่าน LINE API หรือดูผลใน Simulator/มือถือจริง; ต้อง restart/redeploy เพื่อโหลด template ใหม่ และการ์ดเก่าในแชทไม่เปลี่ยนตาม

ข้อเสนออื่นด้าน Business Logic และความทนทานในรายงานเดิมด้านล่างยังไม่ได้ดำเนินการตามขอบเขตล่าสุดของผู้ใช้

## ข้อสรุป

ปรับให้สวย อ่านง่าย และกระชับขึ้นได้โดยรักษา flow เดิม แนะนำใช้ bubble `mega` เป็นฐาน จัดลำดับสถานะ → ข้อมูลที่ต้องพิจารณา → ปุ่มดำเนินการ ลดพื้นที่โลโก้ ใช้ปุ่มเต็มความกว้างเมื่อข้อความยาว และแยกหน้าตาของการ์ดอนุมัติตามบริบทสองประเภท โดยคง action และ state transition เดิม

การลดความสูงควรมาจากการลดภาพและข้อความซ้ำ ไม่ใช่ลดขนาดตัวอักษรหรือซ่อนข้อมูลสำคัญ ยังไม่ควรกำหนดความสูงตายตัว เพราะชื่อภาษาไทย เหตุผล และการตั้งค่าขนาดอักษรทำให้แต่ละเครื่องแสดงผลต่างกัน

## สิ่งที่ตรวจจริงและขอบเขตความมั่นใจ

- อ่าน JSON ทั้ง 4 ไฟล์ พร้อม LineMessageService, จุดเรียกการ์ดใน ChatFlowManager, BalloonFlowService และ LineWebhookController รวมถึง postback handlers และ tests ที่เกี่ยวข้อง
- ตรวจ JSON และ action ปัจจุบัน: template ทั้งสี่ parse ได้ ขนาดไฟล์ประมาณ 1.6–3.6 KB ก่อนแทนค่าจริง
- รัน `./gradlew test --offline`: ผ่าน 68 tests จาก 15 suites ไม่มี failure/error/skipped
- ตรวจ source ของ LINE Java SDK 8.4.0 ที่ใช้อยู่: FlexText และ FlexButton รองรับ `scaling` และ FlexBubble มี `hecto` อย่างไรก็ตามแนวทางนี้เลือก mega เป็นฐาน
- ตรวจอัลกอริทึม escape ปัจจุบันด้วยตัวอย่าง backslash, tab และ newline: บางค่าทำให้ JSON ไม่ถูกต้อง ส่วน newline ถูกแปลงเป็นช่องว่าง
- ยังไม่ได้ทดสอบ Flex Simulator, LINE validate endpoint หรืออุปกรณ์จริง จึงระบุการตัดข้อความและความสูงเป็นความเสี่ยงจาก layout ไม่ใช่ภาพที่ยืนยันแล้ว
- ชุด tests เดิมช่วยยืนยัน baseline เท่านั้น ยังไม่รับรองหน้าตาหรือการส่ง Flex ทั้งหมด และไม่มี LineMessageServiceTests โดยตรง

## การ์ดและ flow ที่ต้องรักษา

| การ์ด | ใช้เมื่อ | พฤติกรรมที่ต้องคงไว้ |
|---|---|---|
| welcome_card.json | Follow event และข้อความเมนู `ทันใจทันใช้` เมื่อไม่อยู่ในโหมดแอดมิน | ปุ่มส่ง message text เดิมสองค่า |
| admin_approval_card.json: ตรวจภาพ | ลูกค้าระบุส่งรูปรอบเครื่องครบแล้ว | ตั้ง ADMIN_PHOTO_CHECK; approve ไป STEP_9_APPROVED_PHOTO แล้ว flow ขอรูปหน้าตั้งค่าและไป STEP_10_NAME |
| admin_approval_card.json: ตรวจข้อมูล | ลูกค้าส่งชื่อใน STEP_11_SUBMIT_DATA | ตั้ง ADMIN_MODE; approve ไป STEP_5_PRICING และเรียก flow เสนอราคา หากมีราคาไป STEP_6_MONTH_SELECTION หากไม่มีส่งต่อแอดมิน |
| emergency_card.json | ขอคุยคน, iCloud, AI ส่งต่อ, ไม่เข้าเกณฑ์, ไม่มีราคา หรือ retry ถึงเกณฑ์ | take_case พักบอท; resume_bot ใช้ previousState หรือ STEP_1_INFO |
| success_card.json | ลูกค้าเลือกระยะเวลาที่มีในตารางราคาของรุ่นนั้น | ตั้ง ADMIN_MODE; take_case ให้แอดมินสรุปยอดและขอเอกสาร ไม่ใช่ยืนยันว่าจ่ายเงินหรือปิดสัญญาแล้ว |

รายละเอียดที่ห้ามมองข้าม:

1. `สนใจผ่อนบอลลูน` เป็นคำสั่งตรงตัวสำหรับเริ่ม flow ใหม่ แม้ขณะ ADMIN_MODE/ADMIN_PHOTO_CHECK ผ่าน ChatFlowManager จึงต้องคง action.text นี้ไว้
2. `สนใจจำนำ iCloud` ส่งต่อแอดมินได้กลาง flow บอลลูน แต่ถูกเช็คหลังเงื่อนไขบอทเงียบ จึงไม่ได้ทำงานเหมือนปุ่มบอลลูนในทุก state
3. `ทันใจทันใช้` แสดงการ์ดโดยไม่ reset flow และยังเงียบเมื่ออยู่โหมดแอดมิน
4. ปุ่มอนุมัติใช้ `action=approve`; ปฏิเสธใช้ `action=reject`; รับเรื่องใช้ `action=take_case`; คืนบอทใช้ `action=resume_bot`
5. คง `service` และ `userId` ใน postback data แม้ handler ปัจจุบันอ่าน action/userId เป็นหลัก และพิจารณาตาม state ในฐานข้อมูล ไม่ได้ใช้ service เลือกเส้นทางอนุมัติ
6. ปุ่มรับเรื่องไม่ได้เปิดห้องสนทนาโดยตรง แต่เปลี่ยน state และตอบข้อความให้แอดมินไปสนทนา 1-on-1 เอง ห้ามเปลี่ยนเป็น URI หรือเขียนป้ายว่าเปิดแชทโดยไม่มีฟังก์ชันรองรับ
7. คงผู้รับแต่ละจุดเรียกเดิม รวมถึงกรณี panic ซึ่งใช้การตั้งค่ากลุ่มแยกจาก flow หลัก

## ปัญหาที่พบ

### 1. การ์ดอนุมัติสื่อความหมายผิดในบางขั้นตอน — สำคัญที่สุด

หัวข้อเขียนว่า “รอตรวจสภาพเครื่อง” และปุ่ม “สภาพผ่าน” ตายตัว แต่ STEP_11_SUBMIT_DATA ใช้การ์ดเดียวกันเพื่อตรวจข้อมูลก่อนเสนอราคา จึงทำให้คนกดเข้าใจผลของปุ่มไม่ตรงกับระบบ

แนวทาง: ส่งบริบทแสดงผล PHOTO_REVIEW หรือ DATA_REVIEW จากจุดเรียกที่รู้อยู่แล้ว ใช้หัวข้อและ label ต่างกัน แต่ใช้ approve/reject เดิม ไม่เลือกประเภทจากการค้นคำในชื่อบริการ และไม่อ่านฐานข้อมูลเพิ่มเพื่อเดาบริบทใน renderer

### 2. หัวข้อยาวไม่มี wrap และข้อมูลซ้ำ

หัวข้อใน template และข้อความ `บริการ: {{SERVICE_NAME}}` ไม่มี wrap; กรณีตรวจภาพ serviceName เป็น “ตรวจสภาพเครื่อง (ผ่อนบอลลูน)” จึงยาวมากเมื่อใช้ xl ส่วนแถว “รุ่น” ได้ค่าซึ่งขึ้นต้น “รุ่น:” อยู่แล้ว รวมถึงคำแนะนำตรวจรูป จึงปะปนข้อมูลกับคำสั่งงาน

แนวทาง: แยกสถานะ, ชื่อบริการ, รุ่น/ความจุ, ข้อแนะนำเป็นคนละ component; หัวข้อ md/lg พร้อม wrap; ไม่ใช้ maxLines ตัดชื่อ รุ่น หรือข้อความสำคัญ

### 3. ปุ่มสองคอลัมน์กินพื้นที่ข้อความ

welcome และ emergency มีปุ่มคู่แนวนอนและ height sm โดยเฉพาะ “แอดมินรับเรื่อง” มีพื้นที่เพียงครึ่งการ์ด เสี่ยงต่อการอ่านไม่ครบและกดยากเมื่อใช้ฟอนต์ใหญ่

แนวทาง: welcome ใช้สองปุ่มเต็มแถวเพื่อให้เลือกบริการได้ชัด; emergency ให้ “รับเรื่อง” เป็น primary เต็มแถว และ “ให้บอททำงานต่อ” เป็น secondary แถวถัดไป; ใช้ height md แล้วลดความสูงจากพื้นที่ภาพและข้อความซ้ำแทน สำหรับ approval ใช้แนวตั้งเป็นค่าเริ่มต้นเพื่อแยกการตัดสินใจ

### 4. ลำดับภาพและสี

welcome ใช้ hero 20:13 แบบ cover ซึ่งกินพื้นที่แนวตั้งมากและอาจครอปโลโก้ ขึ้นกับสัดส่วนไฟล์จริง ส่วนแอดมินใช้สีสดหลายสีและชื่อบริการ xl เด่นกว่าข้อมูลที่ต้องตัดสินใจ

แนวทาง: โลโก้ขนาดเล็กใน header หรือกล่องภาพที่กำหนดพื้นที่เหมาะสมและใช้ contain หลังตรวจ asset จริง; สถานะเด่นหนึ่งจุดต่อการ์ด; พื้นขาวและข้อความเข้ม; ใช้สีร่วมกับข้อความบอกสถานะเสมอ

คำนวณ contrast กับสีขาวจากค่าสีใน template: #00B900 ≈ 2.64:1, #17A2B8 ≈ 3.04:1, #FF4B4B ≈ 3.30:1, #AAAAAA ≈ 2.32:1 สีเหล่านี้บางตำแหน่งอ่านยากบนข้อความขนาดเล็ก แนะนำเขียว #047857 (≈5.48:1) และข้อความรอง #4B5563 (≈7.56:1) โดยตรวจคู่สีจริงของแต่ละ component อีกครั้ง

### 5. การ์ดส่งต่อใช้คำว่า “ฉุกเฉิน” กับทุกกรณี

emergency_card ถูกใช้กับการสนใจ iCloud และการส่งต่อทั่วไปด้วย จึงไม่ควรทำให้ทุกใบดูเป็นเหตุเร่งด่วนเท่ากัน แนะนำหัวข้อกลาง “รอแอดมินดูแล” และแสดงเหตุผลจริงให้ชัดเจน โดยไม่เปลี่ยนเงื่อนไขการส่งต่อ

### 6. รายละเอียดหลายบรรทัดถูกทำให้เป็นข้อความต่อกัน

escapeJson แปลง newline เป็นช่องว่าง ทำให้รุ่น ระยะเวลา และยอดต่องวดใน success card อ่านต่อเนื่องในช่องแคบ อีกทั้งแถว “รายละเอียด” ใช้ flex 1 ต่อค่า flex 3 แต่ label ไม่มี wrap

แนวทาง: success แยกเป็น รุ่น / ความจุ / ระยะเวลา / ยอดต่องวด และข้อความ “รอแอดมินสรุปยอดและขอเอกสาร”; หากยังใช้ extraInfo ให้แสดงเต็มความกว้างใต้ label และเก็บ newline อย่างถูกต้อง

### 7. ความทนทานของ renderer และการส่งข้อความ

- escapeJson จัดการ quote แต่ไม่ได้ escape backslash และ control characters ครบ ทำให้บางชื่อหรือข้อความใช้สร้าง JSON ไม่ได้ ควรเติมข้อมูลลง JsonNode หรือ SDK model แล้วให้ Jackson serialize แทนการแทนค่าลง raw JSON
- String.replace หลายรอบอาจแทน token ที่ปะปนอยู่ในค่าของผู้ใช้ภายหลัง ควรแทนเฉพาะ template node จากต้นฉบับ ไม่ประมวลผลค่าผู้ใช้เป็น template ซ้ำ
- executePushMessage ไม่ observe CompletableFuture จึงไม่เข้า catch สำหรับ asynchronous failure บางชนิด ต้องจัดการผลสำเร็จ/ผิดพลาดจริงและ fallback อย่างชัดเจน
- fallback แบบ text สูญเสียปุ่มดำเนินการ ควรบอกตัวตนเคสและรายละเอียดพอให้แอดมินดำเนินงานต่อได้ โดยไม่สร้างปุ่มหรือคำสั่งใหม่ที่ระบบยังไม่รองรับ
- initTemplates อ่าน template แต่ไม่ได้ validate ทุกใบก่อนเปิดใช้งาน และ catch รวมทั้งชุด ควรเพิ่ม startup validation พร้อมระบุชื่อไฟล์ที่เสีย ส่วนการ fail startup หรือเปิดบริการแบบลดความสามารถต้องกำหนดให้ชัดในงานความทนทาน

ประเด็นเหล่านี้ควรมีชุดแก้และ tests ของตัวเอง เพื่อให้ทบทวนผลต่อการส่งข้อความได้ชัดเจน กรณี timeout ไม่ควร retry ด้วย request ID ใหม่โดยไม่พิจารณาการส่งซ้ำ เพราะ LINE อาจรับข้อความไปแล้ว

## Design specification ที่เสนอ

| ส่วน | ค่าเริ่มต้นเสนอ |
|---|---|
| Bubble | mega ทุกใบในรอบแรก ไม่กำหนดความสูงทั้งใบ |
| Padding | body/footer 16px; header 12–16px |
| Spacing | ภายในกลุ่ม 4–8px; ระหว่างกลุ่ม 12px |
| หัวข้อ | md/lg, bold, wrap true |
| ข้อมูลหลัก | sm/md, สีเข้ม, wrap true |
| ข้อมูลรอง | sm; xs เฉพาะข้อมูลอ้างอิงที่ไม่ใช่ข้อมูลตัดสินใจ |
| ปุ่ม | label กระชับ; height md; ปุ่มยาวเต็มความกว้าง |
| รูปภาพ | โลโก้ขนาดเล็กเฉพาะ welcome; ไม่มี hero ตกแต่งในการ์ดแอดมิน |
| Accessibility | ลอง scaling true กับ text/button ที่เหมาะสม และทดสอบฟอนต์ใหญ่จริง |

การจัดวางเสนอ:

- Welcome: โลโก้เล็ก + ชื่อร้าน → ข้อความต้อนรับสั้น → เลือกบริการ → ปุ่มผ่อนบอลลูน / จำนำ iCloud
- Photo review: “รอตรวจสภาพเครื่อง” → ลูกค้า → รุ่นและความจุ → รหัสอ้างอิง → ข้อความให้ตรวจรูปในแชทเดิม → “สภาพผ่าน” / “ไม่ผ่าน”
- Data review: “รอตรวจข้อมูลและประเมินเครดิต” → ลูกค้า → รุ่นและความจุ → รหัสอ้างอิง → “อนุมัติและเสนอราคา” / “ไม่ผ่าน”
- Handoff: “รอแอดมินดูแล” → บริการ → ลูกค้า → เหตุผลเต็มความกว้าง → “รับเรื่อง” / “ให้บอททำงานต่อ”
- Success: “ลูกค้าเลือกจำนวนงวดแล้ว” → ลูกค้า → รุ่น/ความจุ → จำนวนเดือนและยอดต่องวด → “รับเรื่องและขอเอกสาร”

คง userId เต็มใน payload ทุกกรณี รอบแรกให้เก็บรหัสเต็มที่แสดงบนการ์ดอนุมัติไว้เป็นข้อมูลรองพร้อม wrap; ยังไม่ย่อทิ้งจนกว่าจะมีวิธีระบุลูกค้าทดแทนที่ใช้งานได้จริง ไม่เพิ่มราคา ดอกเบี้ย ยอดโอน หรือสถานะชำระเงินที่โค้ดปัจจุบันไม่ได้ยืนยัน

## ขอบเขตการแก้ตามลำดับ

1. เพิ่ม tests ตรวจ action contract และผล transition สำคัญก่อนแก้: การอนุมัติภาพ การอนุมัติข้อมูล การปฏิเสธ และเมนูทั้งสองบริการ
2. ปรับ JSON ทั้ง 4 ใบด้านสี spacing typography wrap และ footer โดยรักษา action type/text/data เดิม
3. เพิ่มบริบทการแสดงผลของ approval สองแบบใน LineMessageService และจุดเรียกสองแห่งใน BalloonFlowService; เปลี่ยนเฉพาะชื่อหัวข้อ label และ displayText ให้ตรงงาน
4. แยกข้อมูลแสดงผลเป็น fields ที่มีความหมาย โดยรับค่าจาก flow เดิม เช่น selectedMonths และ paymentFor(selectedMonths); ห้ามคำนวณราคาใหม่ใน renderer และไม่จำเป็นต้องแก้ schema ฐานข้อมูล
5. แก้ JSON serialization และ asynchronous error handling แยกเป็นชุดที่ตรวจสอบได้ พร้อม regression tests
6. ตรวจ payload หลังผ่าน SDK serialization, LINE validate endpoint, Flex Simulator และอุปกรณ์จริง จากนั้นจึงนำขึ้นใช้งาน; templates ถูก cache ตอน startup จึงต้อง restart/redeploy ให้ค่ามีผล

ไฟล์หลักที่จะเกี่ยวข้อง: src/main/resources/flex/*.json, service/line/LineMessageService.java, service/flow/BalloonFlowService.java และ tests ที่เกี่ยวข้อง ในงานดีไซน์ไม่จำเป็นต้องแก้ state routing ใน ChatFlowManager หรือ LineWebhookController

## ความเสี่ยงเดิมที่ดีไซน์อย่างเดียวแก้ไม่ได้

1. การ์ดเก่ากดย้อนหลังได้: approveCase ดู state ปัจจุบัน ถ้าไม่ใช่ ADMIN_PHOTO_CHECK จะเข้าทางเสนอราคา ปุ่มเดิมจึงอาจให้ผลต่างกันเมื่อ state เปลี่ยน ต้องแยกพิจารณาเรื่อง case/version/state guard เพราะเป็นการเปลี่ยนพฤติกรรม ไม่ใช่แค่จัดหน้าการ์ด
2. resume_bot ไม่ได้รับประกันว่าจะมี automated flow ให้ทุก service; iCloud ไม่มี handler และ resumeBot เติม service เฉพาะเมื่อ service ว่าง จึงห้ามเขียน UI ว่า “ทำขั้นตอนอัตโนมัติต่อทันที” สำหรับทุกเคส
3. Flow ใช้ marker [รูปภาพ] และข้อความลูกค้าที่ระบุว่าส่งครบ ไม่ได้ส่งรูปเครื่องจริงเข้า approval card ในเส้นทางที่ตรวจ; ไม่ควรออกแบบปุ่ม “ดูรูปทั้งหมด” จนกว่าจะมีแหล่งภาพและฟังก์ชันเปิดดูจริง
4. การเปลี่ยน JSON ใหม่ไม่แก้ข้อความเก่าที่ส่งไปแล้ว จึงต้องคงการรองรับ action เดิม

## เกณฑ์ตรวจรับ

- เปรียบเทียบ action type/text/data ของทุกปุ่มกับ baseline; label/displayText เปลี่ยนได้ตามแผน แต่ userId/service/action ต้องเท่าเดิม
- ทดสอบ welcome ใน state ใหม่, กลาง flow, ADMIN_MODE และ ADMIN_PHOTO_CHECK แยกบอลลูนกับ iCloud เพราะลำดับเงื่อนไขต่างกัน
- ทดสอบ approve ภาพ → ขอรูปตั้งค่า, approve ข้อมูล → ราคาเดิม/งวดเดิม, ไม่มีราคา → แอดมิน, reject → REJECTED
- ทดสอบ take_case/resume_bot รวม previousState และพฤติกรรม reminder เดิม
- ทดสอบชื่อไทยยาว, emoji, quote, backslash, tab, newline, null และข้อความคล้าย placeholder
- ทดสอบ success ใช้จำนวนเดือนและยอดต่องวดจากตารางจริง; ไม่มีการกล่าวว่าปิดการขาย/ชำระแล้ว
- ตรวจขนาด JSON หลังเติมข้อมูลจริงและหลัง serialize ผ่าน SDK รวมถึงความยาว action data/displayText/altText ตาม LINE API ปัจจุบัน
- จำลอง API failure แบบ asynchronous แล้วตรวจ fallback และไม่มี state transition หรือการส่งซ้ำโดยไม่ตั้งใจ
- ตรวจ Simulator และ LINE บน iOS/Android อย่างน้อยจอแคบกับฟอนต์ปกติ/ใหญ่: หัวข้อไม่หาย ชื่อ/รุ่น/เหตุผลอ่านครบ ปุ่มไม่ตัดจนเข้าใจผิด ไม่มีโลโก้ครอปผิดสัดส่วน

## แหล่งข้อมูล LINE ทางการ

- [Send Flex Messages](https://developers.line.biz/en/docs/messaging-api/using-flex-messages/): การแสดงผลขึ้นกับ OS, รุ่น LINE, ความละเอียด ภาษา และฟอนต์ จึงยืนยันหน้าตาด้วย JSON อย่างเดียวไม่ได้
- [Messaging API reference](https://developers.line.biz/en/reference/messaging-api/nojs/): bubble JSON สูงสุด 30 KB, mega เป็นค่าขนาดเริ่มต้น, label ของ Flex button สูงสุด 40 ตัวอักษร, altText สูงสุด 1500 ตัวอักษร ทั้งนี้จำนวนตัวอักษรที่ API รับได้ไม่เท่ากับจำนวนที่ปุ่มแสดงอ่านได้ครบ
- [Flex Message layout](https://developers.line.biz/en/docs/messaging-api/flex-message-layout/): ความกว้างสัมพันธ์กับหน้าจอ และ scaling ช่วยปรับตามการตั้งค่าขนาดอักษรของ LINE

ข้อเสนอขนาดและสีในเอกสารนี้เป็น design recommendation จากโค้ดที่ตรวจ ไม่ใช่ผลวัดความพึงพอใจผู้ใช้หรือผล render บนอุปกรณ์จริง
